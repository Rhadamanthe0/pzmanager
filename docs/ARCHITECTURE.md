## Repo layout

At the root: `pzm` (dispatcher), `.env` (live config + secrets, gitignored), `logs/` (gitignored), `versionning/` (mod-list ledger + `sheetVersionning.sh`; the `V*.txt` and `Mods bugués*.csv` inside are gitignored), `docs/`, `Zomboid/`. Everything else lives under `data/`: `scripts/` (all the code, plus the bootstrap `install.sh`), `setupTemplates/`, `pzserver/`, `dataBackups/`, `fullBackups/`.

## Dispatcher and script layers

`pzm` (root) parses the command and `exec`s into `data/scripts/<layer>/`:
- `data/scripts/core/pz.sh` — server lifecycle (start/stop/restart/status), player warnings, reason/automatic/silent handling.
- `data/scripts/admin/` — maintenance, reset, whitelist, mod-update trigger, creation-date init.
- `data/scripts/backup/` — incremental (`dataBackup.sh`) and full/sync (`fullBackup.sh`) backups, restore.
- `data/scripts/install/` — `setupSystem.sh` (apt, user, systemd units, sudoers) and `configurationInitiale.sh` (SteamCMD install, config).
- `data/scripts/internal/` — helpers not called directly by users: `sendCommand.sh`, `sendDiscord.sh`, `captureLogs.sh`, `configureJvm.sh`, `notifyServerReady.sh`.
- `data/scripts/discord/` — **inbound** Discord command bot (Python/discord.py, the only non-Bash component): `bot.py` exposes a `/pzm …` slash-command group mirroring the dispatcher (`server`/`backup`/`whitelist`/`admin`/`install` subgroups + `rcon`/`discord`/`help`); every subcommand builds a fixed argv and runs `pzm` via `subprocess` (never a shell → "pzm only", no injection). Output comes back as one message (inline code block, or a `pzm-output.txt` attachment when it exceeds one block). **Batch**: an `on_message` handler runs a pasted message whose every content line is `pzm …` line-by-line (sequential, same `run_lock` as the slash commands), deletes the source message, and posts one recap; all-or-nothing (one bad line cancels the whole batch, nothing runs/deletes). Concurrent invocations (slash or batch) **queue** on `run_lock` (asyncio FIFO) rather than being rejected — a batch shows "en file d'attente…" until its turn. `run-bot.sh` sources `.env` and execs the venv Python; `requirements.txt` pins `discord.py`. Installed by `data/scripts/install/setupDiscordBot.sh` (`pzm install discord`), which builds the gitignored `.venv` and enables `pz-discord-bot.service`. Distinct from the outbound `sendDiscord.sh` webhook.
- `data/scripts/lib/common.sh` — sourced by every script: `source_env`, `die`/`log`, directory helpers, and the **maintenance lock** (`try_acquire_maintenance_lock`) shared across `pz.sh`, modcheck, and maintenance to serialize conflicting operations.

## Configuration

All paths, ports, retention, the Discord webhook and the Google service-account key live in `.env` **at the repo root** (gitignored, chmod 600). `source_env` auto-creates it from `data/setupTemplates/.env.example` on first run. It takes **no argument**: `common.sh` derives the install root from its own location (`PZ_MANAGER_ROOT`, three levels up from `data/scripts/lib/`), so only that one line depends on the tree depth — scripts never count `..` themselves. Never hardcode paths — read them from the exported `PZ_*`, `BACKUP_*`, `LOG_*` variables.

### The Google Sheets key has no file

`versionning/sheetVersionning.sh` reads `GOOGLE_SERVICE_ACCOUNT_JSON_B64` (base64 of the whole service-account JSON) and `SHEET_VERSIONNING_ID` from `.env`, decodes the key into a chmod-600 temp file it deletes on exit. There is deliberately no `.json` key on disk, and the spreadsheet ID is not in the (now versioned) script.

## Server control is a FIFO, not RCON-over-TCP

This is the central, non-obvious design:
- `zomboid.socket` (systemd) creates a named-pipe FIFO at `data/pzserver/zomboid.control`.
- `zomboid.service` launches `start-server.sh` with **stdin bound to that FIFO** (`<> .../zomboid.control`).
- Sending a server command = writing a line to the FIFO. `sendCommand.sh` does this, then scrapes the **command output back out of journald** (matching `command entered via server console`). `pzm rcon` is a thin wrapper over `sendCommand.sh`.
- `ExecStop` writes `quit` to the pipe for a clean shutdown.
- `zomboid_logger.service` (`captureLogs.sh`) runs alongside and persists logs.
- The admin password is passed once via a `.admin_password` file that `ExecStart` reads and immediately deletes.

## Automation

All timers are systemd `--user` units.
- `pz-backup.timer` — hourly at minute 14, incremental hardlinked snapshot (`dataBackup.sh`). **Its in-game `save` is now the server's ONLY periodic write to disk — never remove it.** Since 2026-08-16 `SaveWorldEveryMinutes=0` in `servertest.ini` (was 5): every save runs `ServerMap.SaveAll` **synchronously on the main loop**, and past 600 ms PZ literally freezes everyone (`Pausing clients because saving is taking longer than 600ms` in the game log) — measured 679 ms on a normal run, 2 969 ms worst case, and minute `:14` alone accounted for 24% of all pause events over 7 days. That is the "micro-lag à chaque heure 15" players reported. Going to 0 cut save-induced main-loop stalls from ~87/day to 24/day; the admin explicitly accepted the resulting **1-hour RPO** on an unclean death (hard box freeze / heap OOM — a clean `pzm server stop` still saves via `ExecStop`). Corollary: the frame counter `f:` + server clock `st:` in the game log are the fine-grained stall signal (one frame spanning 679 ms = the freeze); system-wide I/O pressure during the rsync measured only ~2% (`/proc/pressure/io`), so the **rsync is not a lag source** — the `CPUQuota=20%` throttle works. **GFS retention** (`prune_gfs`, not a flat N-day rotation): hourly granularity for `BACKUP_GFS_HOURLY_HOURS` (24h), then 1 per 6h to `BACKUP_GFS_SIXHOURLY_DAYS` (7d), then 1 per day to `BACKUP_GFS_DAILY_DAYS` (30d) — thins the pile from ~413 to ~62 (→~82 once 30d of history accrues). Each snapshot is complete & independent (hardlinks), so pruning one never touches another. rsync is CPU-throttled by the unit (`CPUQuota=20%`, `TimeoutStartSec=2400`) with `--partial` + retry ×3; codes 23/24 (files vanished on a live world) stay benign. A `flock` (fd 201, `/tmp/pzmanager-backup-<user>.lock`) makes the run **single-instance** — a run can be long (deleting a hardlinked snapshot = hundreds of thousands of `unlink()`, slow at 20% CPU), so `prune_gfs` deletes at most `BACKUP_PRUNE_MAX_DELETE` (15) snapshots per run and a large backlog drains cleanly over several hourly runs instead of being killed mid-prune at the timeout (which spammed hourly "failed" Discord alerts on 2026-07-25 before the timeout was raised 600→2400 and the cap added). `BACKUP_PRUNE_DRY_RUN=1` previews the prune without deleting. Off-site is separate: `fullBackup.sh` keeps `OFFSITE_BACKUP_COUNT` (7) **single self-contained ZIPs** (by count) named `fullBackups/<ts>.zip`, mirrored by a root **Syncthing** send-only folder → the admin's PC → Google Drive. Each ZIP holds only the **valuable, non-reconstructible** data — `config/` (`.ssh`, systemd `--user` units, `setupTemplates`, `scripts/` incl. `.env`, `sudoers.d/<user>`) + `zomboid/` (the latest `Saves`/`db`/`Server` snapshot, dereferenced from `dataBackups/latest`) — and **excludes** everything re-downloadable (`data/pzserver` = SteamCMD install + Workshop mods, the local backups themselves, logs, the Discord venv). The ZIP is the transport format because Syncthing has no hardlink awareness — a hardlinked tree would explode ~66× on the PC; `zip -r` flattens the hardlinked snapshot (it dereferences the `latest` symlink). Built in a `.<ts>.zip.partial` in the same dir then `mv`'d (atomic same-fs rename) so Syncthing never sees a half-written ZIP. **Restore** (`configurationInitiale.sh restore <ts>.zip`) unzips to a temp dir and maps `config/` back via the `$PZ_HOME`-relative convention + restores `zomboid/` into `PZ_SOURCE_DIR`; it still accepts the **old dir-format** backups (inner `Zomboid_Latest_Full.zip`) for backward compat while the retention purges them.
- `pz-modcheck.timer` — every 5 min; calls `triggerMaintenanceOnModUpdate.sh`, which splits the two cases: a **mod** update triggers only a **short-delay restart** (the PZ server re-downloads the Workshop item itself at boot, so nothing more is needed), while a **server/build** update triggers the full maintenance (apt, `app_update … validate`, JVM re-tune, reboot). It used to run the full maintenance — and therefore reboot the box — for every mod update, several times a day, for no benefit: maintenance's `download_workshop_mods()` pre-pull early-returns while `STEAM_LOGIN` is anonymous, and `app_update` concerns the build, not mods. The reason string names the updated mods (see `listOutdatedMods.sh` below).
- `data/scripts/internal/listOutdatedMods.sh` — names the mods whose Steam copy is newer than the local one. The console command `checkModsNeedUpdate` only answers with a global status and **never names the mod**, so this compares `timeupdated` in `steamapps/workshop/appworkshop_108600.acf` (section `WorkshopItemsInstalled` only — `WorkshopItemDetails` repeats the same IDs) against `time_updated` from Steam's `ISteamRemoteStorage/GetPublishedFileDetails` (no API key needed), which also returns the human-readable title. Empty output = unknown → the caller falls back to the generic reason rather than announcing a wrong list.
- `pz-maintenance.timer` — daily 04:30; `performFullMaintenance.sh` stops the server, runs `apt upgrade`, `steamcmd +app_update … validate`, **re-applies JVM tuning**, syncs, and optionally reboots (`REBOOT_ON_MAINTENANCE`). It no longer triggers the inactive-access purge — that moved to `zomboid.service`'s `ExecStartPre` (see gotchas).
- `pz-creation-date-init.timer` — midnight; feeds the **account-age ledger** used by the inactivity purge. `creationDateInit.sh` appends one line per newly-seen account to `WHITELIST_LEDGER` (`data/whitelistLedger.csv`, `username;steamid;created_at`, chmod 600, gitignored). It lives **outside the world DB on purpose**: the DB is recreated by every wipe, and the `created_at` column this script used to fill **never existed** (no `ALTER TABLE` anywhere) — so from install until 2026-08-19 the timer was a guaranteed no-op and the purge fell back to a branch that treated *any* never-connected account as inactive regardless of age. Rules: `created_at` is written **only on first sighting** and never modified; no line is ever deleted (a returning player keeps his real age); a never-connected account **absent from the ledger is never purged** (unknown age -> abstain); on first population `created_at` = `lastConnection` when set, else now (both under-estimate age, so they delay a purge — the safe direction). `lastConnection` is deliberately **not** duplicated: `resetServer.sh` re-injects it into the new DB at wipe time (verified — oldest date in DB 2026-06-19 predates the 2026-08-05 world recreation). The script is **read-only on the DB**, so it runs fine with the server up; `purgeInactivePlayers.sh` calls it before deciding, so an account restored by a wipe is registered before being judged. The ledger sits in `data/` (untouched by `pzm admin reset`) and is in `fullBackup.sh`'s `DIRS_TO_SYNC` — the incremental snapshots only cover `Zomboid/`.
- `pz-heapcheck.timer` — **adaptive** memory-driven restart (replaced the old fixed 11/17/23h `pz-restart.timer`). Fires ~every 3 min (`OnUnitInactiveSec=3min`, so it never overlaps its own run) → `pz-heapcheck.service` (oneshot, `TimeoutStartSec=1500`) → `data/scripts/internal/checkHeapAndRestart.sh`: reads the **post-major-GC heap %** from `logs/zomboid/gc.log` (the `Major Collection … ->NNNNM(PP%)` line = live set after a full GC) and when it reaches `HEAP_RESTART_PERCENT` (`.env`, default **95**) triggers `pzm server restart HEAP_RESTART_DELAY` (default `5m`, `--automatic`). A `/tmp/pzmanager-heapcheck-*.trigger` cooldown marker (1800 s) prevents re-triggering during the warning. **Mitigates the recurring Java-heap OOM** (see gotchas) by restarting *when the heap is actually near full* instead of on a blind schedule — restarts only when needed (quiet server = no needless restart) and catches a fast-filling heavy session before it OOMs. The **04:30 maintenance restart is the daily backstop** if the monitor ever fails to fire. gc.log stays fresh enough to read: ZGC `ZCollectionInterval=60` forces a **major** collection every 60 s, so the ~3-min monitor always finds a recent `Major Collection` line (the heap takes ~15 h to fill — one major/min is ample). Tuning trade-off: at post-GC 95% the heap can't free below 95%, so a long warning risks OOM mid-countdown — lower `HEAP_RESTART_PERCENT` to 90 or shorten `HEAP_RESTART_DELAY` if a crash ever happens during the warning.
